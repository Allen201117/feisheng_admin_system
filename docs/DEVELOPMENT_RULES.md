# 开发规则

## 每次开发前

- 必须先阅读 `docs/PROJECT_MEMORY.md` 和 `docs/ARCHITECTURE.md`。
- 必须确认本次修改涉及哪些高风险区域：工资、权限、时间、统计、导出、数据库字段、订单删除、发薪锁定。
- 必须先输出 Plan，再执行修改。
- Plan 中要说明：修改范围、涉及文件、数据字段、兼容旧数据方式、测试路径。

## 禁止行为

- 禁止不读项目记忆文档就直接改代码。
- 禁止猜数据库字段、猜业务口径、猜权限规则。
- 禁止一次性大规模重构。
- 禁止复制第二套工资、考勤、统计、导出逻辑。
- 禁止在页面层堆复杂业务计算。
- 禁止吞错 `catch`，尤其是工资、权限、考勤、统计、导出、数据库写入、审计日志相关逻辑。
- 禁止私自修改工资口径、质检计薪口径、发薪锁定规则、权限矩阵、北京时间口径。
- 禁止为了“兜底可用”写隐藏数据错误的兼容逻辑。

## 数据库字段规则

- 新增字段必须说明用途、来源、写入位置、读取位置、默认值、兼容旧数据方式。
- 修改字段含义必须同步更新 `PROJECT_MEMORY.md` 和 `ARCHITECTURE.md`。
- 删除字段或改变字段类型前必须单独确认，默认不允许。
- 旧字段兼容只能明确写出规则，不允许靠模糊兜底掩盖错误。

## 工资、考勤、统计规则

- 工资计算只能复用既有统一逻辑或先抽象统一逻辑，不能在页面或新云函数中复制一套。
- 考勤统计必须使用北京时间业务日期和统一时间工具。
- 统计、数据中心、排行榜、导出必须尽量共享同一口径。
- 当前高风险口径：工资目前主要按 `WorkLogs.quantity * snapshot_price` 计算，而不是按 `passed_qty`。修改前必须由业务确认。
- 已发薪月份的数据修改必须遵守发薪锁定或冲正规则。

## 权限规则

- 所有云函数写操作必须校验登录态和角色。
- 读取员工、订单、工序、工价、工资、导出数据时必须明确允许哪些角色访问。
- 员工只能访问自己的工资、考勤、报工，除非规则明确允许。
- QC 只能访问质检所需数据，不能默认拥有老板权限。
- 老板权限也必须基于有效登录态和 `status=active`。

## 时间规则

- 业务日期、跨天、月结、统计周期统一按北京时间 UTC+8。
- 前端和云函数不得直接使用本地时区方法做业务判断。
- `db.serverDate()` 可用于记录真实操作时间。
- `toISOString()` 可用于保存具体时间点，但展示和业务归属必须通过北京时间工具转换。
- 修改任何时间逻辑后必须更新架构文档的时间口径说明。

## 文档同步规则

以下修改完成后，必须同步更新 `docs/PROJECT_MEMORY.md` 和/或 `docs/ARCHITECTURE.md`：

- 页面、路由、云函数 API 变化。
- 数据库集合或字段变化。
- 权限规则变化。
- 工资、质检、发薪锁定、奖惩、冲正规则变化。
- 考勤、定位、时间口径变化。
- 统计、排行榜、数据中心、导出口径变化。
- 订单删除、软删除、归档规则变化。

## 测试与交付规则

- 每次修改后必须说明测试路径，包括运行了哪些测试、手工验证了哪些页面或云函数路径。
- 如果无法运行测试，必须说明原因和残余风险。
- 小功能建议单独 Git commit，避免多个高风险改动混在一个提交里。
- 交付说明必须写清楚：改了什么、为什么改、怎么测、还有什么风险。

## Git 助手规则

每次完成代码任务后，必须自动执行：

1. `git status --short`
2. `git diff --stat`
3. 总结本次改动
4. 生成建议 commit message

但未经用户明确确认，不得自动执行：

- `git add`
- `git commit`
- `git restore`
- `git reset`
- `git clean`
- `git push`

当用户说“确认提交”后，只允许提交本次任务相关文件，不允许使用 `git add .`。提交后必须再次输出 `git status --short`。

## 推荐迭代顺序

1. 先修 P0：权限泄漏、工资口径、删除规则、数据错误。
2. 再修 P1：统计口径统一、性能、导出一致性、吞错排障。
3. 最后修 P2：命名、可读性、样式、文档细节。
