# 飞盛产品、工程与用户体验审查交接

> 审查日期：2026-07-11  
> 审查方式：权威文档与代码静态审查、微信开发者工具只读走查、现有单元测试复核  
> 审查范围：老板端与员工端主流程，兼顾产品方向、架构、数据、安全、测试与无障碍风险  
> 安全边界：未打卡、未提交报工、未发薪、未删除或修改真实数据，未部署、上传或发布

## 1. 必须先记住的业务口径

### 1.1 工资不参考质检数

- 工资唯一口径：`Σ(WorkLogs.quantity × 有效 snapshot_price)`。
- 工资按员工报工数量 `quantity` 计算，**不按合格数 `passed_qty` 计算**。
- `passed_qty` 只用于质量统计、合格率和质检看板，永不进入工资计算。
- 未发薪报工的有效结算价跟随 `Processes.current_price`；已发薪后冻结历史 `snapshot_price`。
- 因此，后续任何“发薪前必须质检完成”“未质检导致工资异常”“按合格数核薪”的产品或工程建议都不符合本项目口径，禁止实现。
- 可以提示老板“存在未质检记录”，但该提示只能用于质量管理，不得阻断发薪或改变工资金额。

### 1.2 已确认的其他高风险口径

- 已发薪工序或订单禁止改价；未发薪改价需同步所有未发薪报工。
- 订单完成状态会锁定相关写操作，但老板可以按既定规则恢复为进行中。
- 老板侧需要同时理解当前工价和历史结算价；两者不同不等于算错。
- 多工厂数据必须按登录用户推导的 `org_id` 隔离，不能信任前端传入的租户值。
- 所有业务日期和周期判断使用北京时间 UTC+8。

## 2. 项目现状与审查证据

### 2.1 已确认事实

- 产品已有 1 个真实工厂、2 名老板和 28 名员工使用。
- 腾讯云环境存在真实业务数据；本次只读走查使用测试账号。
- 走查时老板首页显示 31 名系统用户、5 个进行中订单、626 条待质检和本月薪资支出 8843.38 元。
- 仓库已有订单、工序、报工、质检、工资、考勤、排行榜、数据中心和导出等完整模块。
- `npm run test:unit` 在审查时为 236/236 通过。
- 现有 E2E 仅验证首个配置页面可以打开，没有覆盖员工报工、老板核对、发薪锁、历史工资和跨租户拒绝。
- 审查结束时工作区无既有改动；本交接只新增文档并更新版本记录。

### 2.2 事实与判断边界

以下属于判断，不是已经被数据证明的事实：

- 当前最大价值可能是减少报工与工资核对争议，但尚无争议次数和核对耗时数据。
- 现有功能可能较贴合飞盛单一工厂，尚未证明可以直接复制给其他工厂。
- 626 条待质检可能是正常积压，也可能是质检流程没有被持续执行；需要业务访谈确认。无论原因是什么，它都不影响工资计算口径。
- 老板首页的高频入口排序是基于界面与流程判断，尚未有真实点击数据佐证。

## 3. 总结性结论

项目值得继续做，但当前不建议急着扩厂推广，也不建议继续堆功能。下一阶段应集中处理三件事：

1. 让员工提交的报工和工资展示可信、可解释、无格式错误。
2. 让老板更快发现需要处理的订单、报工、考勤和工资问题，并降低高风险操作误触。
3. 补齐 token 过期、写请求幂等、核心流程 E2E 和真实使用指标。

最关键的判断是：现在缺的不是功能数量，而是“员工正确报工—老板快速核对—工资结果可信”的稳定闭环。

## 4. 产品视角审查

### 4.1 问题是否真实

真实工厂持续使用说明订单、报工、工资和考勤问题确实存在，但目前只有一个工厂样本。这只能证明“飞盛工厂需要”，不能证明“不同行业习惯和管理方式的工厂都需要同一套流程”。

扩厂前建议访谈至少 3 家不同规模工厂，确认：

- 当前用纸张、微信群还是 Excel 记录报工和工资。
- 最痛的是漏报、错报、核对慢、工资争议还是订单进度不透明。
- 发薪周期、改价、质检、返工和订单完成规则是否与飞盛一致。
- 愿意为什么结果付费，而不是愿意为多少功能付费。

### 4.2 用户为什么持续使用

长期留存不应依赖“功能都在一个小程序里”，而应依赖可持续结果：

- 员工报工更快，能看清剩余可报数量和自己的预计工资。
- 老板减少人工核对，能快速找到异常报工和订单风险。
- 双方使用同一份报工数据计算工资，减少争议。

### 4.3 建议的唯一北极星指标

建议使用“每周无人工纠正的有效报工率”：

> 员工提交后 24 小时内没有被编辑或删除，并最终正常进入工资核算的报工数 ÷ 全部报工数。

这个指标同时反映员工是否容易正确提交、老板是否需要大量返工、报工能否进入工资闭环。先采集两周基线，再暂定以持续四周达到 95% 以上为成功线。

配套诊断指标：

- 报工提交成功率和重复提交率。
- 员工自改、自删和老板代改率。
- 老板每周用于核对报工与工资的时间。
- 工资争议次数。
- 报工页面和云函数错误率。
- 质量侧单独统计待质检数量和合格率，不与工资指标混算。

### 4.4 当前应该做与明确不做

应该做：

- 修复工资与金额可信度问题。
- 缩短老板高频任务路径。
- 降低发薪、删订单、清报工和改价等操作的误触概率。
- 建立真实行为、错误和核对成本指标。
- 在隔离测试环境补完整流程 E2E。

暂时不做：

- 新增更多经营报表和首页入口。
- 继续扩充低频设置项。
- 未验证外部工厂前投入复杂商业化和多工厂定制功能。
- 把质检数加入工资计算、发薪阻断或工资异常规则。

### 4.5 更轻的验证路径

1. 现有 28 名员工先埋点记录报工进入、提交、失败、编辑和删除。
2. 两位老板每周记录人工核对时间和代改原因。
3. 访谈 3 家外部工厂，只演示核心闭环，不先开发定制需求。
4. 选择 1 家进行人工辅助试用，异常由人工兜底。
5. 达到有效报工率和核对耗时目标后再决定扩厂。

## 5. 工程视角审查

### 5.1 架构

当前规模下架构可用：前端、云函数和纯逻辑已有分层，关键业务规则有单元测试，鉴权副本也有一致性测试。

主要风险：

- 工资、排行榜、导出和周期统计仍存在多套聚合入口，口径漂移成本高。
- 鉴权、北京时间和结算价公共逻辑需要复制到多个云函数目录，部署漏同步风险长期存在。
- 多个页面和接口采用批量拉取后在内存分组聚合，用户量和报工量增长 10 倍后会增加延迟与内存压力。
- 大订单包含 65 至 116 道工序，页面状态和网络响应已经偏重。

### 5.2 数据与接口

已有优点：

- `org_id` 从登录用户推导。
- 已发薪和未发薪结算价语义明确。
- 删除、改价、订单完成和发薪锁有服务端检查。

优先风险：

1. `session_token` 没有 TTL，泄露后可能长期有效。
2. `callCloud` 对网络错误自动重试，写操作可能在“服务端已成功、客户端未收到响应”时重复执行。
3. 写接口缺少统一 `request_id` 幂等保护。
4. 页面仍有模板直接计算金额，造成浮点误差直接展示。

### 5.3 性能与扩展

增长 10 倍时优先关注：

- 工资、排行、导出和数据中心的大范围读库与内存聚合。
- 大工序订单和报工明细的传输与渲染。
- 多接口串行加载导致数字从默认 0 跳到真实值。
- 缺少按订单、月份和用户维护的增量汇总数据。

暂时不建议为了假设中的 100 倍规模整体重构。应先记录接口耗时、结果数量、云函数内存和超时率，再对真实瓶颈做分页游标、汇总表或增量统计。

### 5.4 测试与工程化

- 236 项单元测试通过只能证明被覆盖的纯逻辑和静态规则，不证明完整用户流程可用。
- 现有 E2E 只验证首页能打开。
- 仓库没有发现自动持续集成流水线，测试依赖人工运行。
- 开发者工具走查时出现 `showLoading 与 hideLoading 必须配对使用` 警告和一次未定位来源的超时错误。

建议建立独立测试组织和测试数据，至少覆盖：

1. 员工提交报工并读回。
2. 同一请求重复发送只生成一条报工。
3. 老板查看同一条报工与工资金额一致。
4. 工资严格按 `quantity × 有效 snapshot_price`，改变 `passed_qty` 不改变工资。
5. 发薪后价格冻结和写锁生效。
6. 员工不能读取他人工资，跨工厂请求被拒绝。
7. 网络超时、重复点击和响应丢失不产生重复写入。

### 5.5 安全与合规

已有基础：隐私勾选默认未选、主接口要求账号和 token、工厂停用时拒绝访问、重要写操作有角色与租户检查。

仍需处理：

- token 签发时间、过期时间、最近使用时间和主动失效。
- 高风险写请求幂等。
- 登录、改价、改报工、删报工、发薪和取消发薪的审计告警。
- 越权和跨租户自动化测试。
- 图标及可点击 `view` 的无障碍语义标签。

## 6. 用户体验走查结论

### 6.1 老板首页

首页同时承担经营看板、功能导航、订阅状态和系统工具，入口多且重复。建议首页只保留：

- 今日待处理：异常考勤、待质检、未分配工序、工资核对提醒。
- 三个主入口：订单、报工、工资。
- 其他功能进入“全部工具”。

“待质检”是质量任务提醒，不是工资风险提醒。

### 6.2 考勤

异常记录在加载初期显示 0，加载后变成 88。加载完成前应显示骨架或“正在统计”，不能用 0 冒充结果。

### 6.3 订单列表

每张卡片同时出现详情、状态、完成和删除。完成与删除会影响后续写锁和工资数据，不应与普通浏览操作同层展示。

建议：

- 卡片点击只进入详情。
- 完成操作进入订单详情的明确流程。
- 删除收进更多菜单，并提前展示受影响记录数。
- 列表优先显示超期、未分配工序和长期无报工等待处理问题。

### 6.4 订单详情

工价隐藏、清空工价、清空报工、工序分配、编辑和删除集中在一个长页面。建议普通操作与危险操作分区，危险操作进入独立“订单管理”区并加强影响说明。

### 6.5 报工管理

当前主要展示所有进度，缺少异常优先级。建议优先呈现：

- 超过订单数量的报工。
- 长时间无人报工的工序。
- 多人协作但进度异常的工序。
- 待质检积压，明确标注为质量任务。

### 6.6 薪酬管理

发薪勾选和普通员工列表浏览处在同一层，容易误触。建议拆成两个阶段：

1. 核对工资金额、奖惩、报工更正和发薪锁冲突。
2. 进入发放确认页，展示人数、总额、付款方式和最终确认。

可以同时展示待质检数量供老板参考，但不得影响工资金额，也不得作为发薪阻断条件。

### 6.7 数据中心

当前手机端主要展示横向 Excel 表格，字段多、需要横向滚动，不适合快速决策。建议默认回答：

- 本期总工资及变化。
- 哪些订单、员工或工序异常。
- 哪些生产环节影响进度。
- 质量指标单独展示待质检和合格率。

完整表格下沉到“查看明细”或“导出 Excel”。

### 6.8 员工首页与工序列表

员工主线相对清楚：工资、排名、打卡、今日报工。建议低频设置移出首页；已报满工序默认折叠；可报工工序继续突出剩余数量和当前可见工价。

### 6.9 报工表单

快捷数量适合高频操作，但还应增加：

- 输入后的本次预计金额。
- 提交后的累计报工数量。
- 防连续点击和重复请求。
- 成功回执：订单、工序、数量、金额和时间。

预计金额仍按报工数量和有效结算价计算，与质检数无关。

### 6.10 历史报工与工资

真实走查复现明细金额显示 `¥43.470000000000006`、`¥26.400000000000002`。根因是 `worklog-history.wxml` 在模板中直接使用 `quantity * snapshot_price`。

这会直接损害员工对工资准确性的信任。所有金额必须在 JS 视图模型层统一格式化为两位小数字符串，模板禁止直接计算金额。

工资页还应补充：

- “预估/已发放”醒目状态。
- 最近更新时间。
- 工资计算说明：报工数量 × 有效结算价。
- 对应报工明细入口和争议反馈方式。
- 合格率可作为独立质量信息展示，但必须明确“不参与工资计算”。

## 7. 问题清单与优先级

### P0：立刻处理

1. **历史报工金额显示浮点误差**  
   影响：员工怀疑工资算错。  
   动作：统一金额格式化，模板禁止金额运算，增加回归测试。

2. **写操作缺少幂等保护但存在自动网络重试**  
   影响：可能重复报工、补卡或奖惩。  
   动作：写请求增加 `request_id`，服务端拒绝重复；完成前只对只读调用自动重试。

3. **session token 无 TTL**  
   影响：泄露后可能长期有效。  
   动作：增加过期、续期和主动失效机制。

4. **缺少工资与报工核心闭环 E2E**  
   影响：单元测试无法发现真实页面金额错误和重复写入。  
   动作：建立隔离测试环境并覆盖报工、工资、发薪锁、价格冻结和租户隔离。

### P1：尽快处理

1. 老板首页入口过多且重复。
2. 订单列表暴露多个高风险操作。
3. 发薪操作与普通浏览混在同一列表。
4. 数据中心照搬横向表格。
5. 缺少北极星指标、纠错率和人工核对耗时。
6. 加载期间默认 0 被当作真实结果。
7. 开发者工具 loading 警告和超时未收口。
8. 图标和可点击区域缺少无障碍语义。

### P2：可延后

1. 低频设置移出首页。
2. 已报满工序默认折叠。
3. 工资页增加更新时间、计算说明和争议入口。
4. 数据中心增加异常与趋势卡片。
5. 统一公共云函数副本的生成或发布机制。

## 8. 推荐执行顺序

1. 修复浮点金额并补回归测试。
2. 收紧写请求重试并设计幂等键。
3. 为 token 增加 TTL 与失效机制。
4. 建立隔离测试组织，补工资与报工闭环 E2E。
5. 埋点统计报工提交、失败、编辑、删除、老板代改和重复请求。
6. 重构老板首页为“待处理 + 三个主入口”。
7. 把发薪重构为“核对—确认—完成”，不引入质检阻断。
8. 把数据中心改为移动端决策摘要，表格降为二级详情。
9. 访谈外部 3 家工厂，验证通用性后再扩厂。

## 9. 每项改动的验收标准

### 9.1 金额格式

- 所有金额固定显示两位小数。
- 不出现长浮点数、`NaN`、`undefined`。
- 同一报工在员工历史、老板报工、工资、排行和导出中的有效结算金额一致。
- 修改 `passed_qty` 不改变任何工资金额。

### 9.2 幂等与重试

- 同一 `request_id` 连续提交多次只产生一条业务记录。
- 模拟服务端成功但客户端响应丢失，重试后仍只有一条记录。
- 按钮提交期间禁用并给出明确状态。

### 9.3 工资闭环

- 工资严格按 `quantity × 有效 snapshot_price`。
- 未发薪使用当前价，已发薪保留历史快照价。
- 改变质检数和合格率不改变工资。
- 发薪锁、改价锁和订单状态锁按权威口径生效。

### 9.4 体验

- 老板首页首屏可以直接看到主要待处理事项。
- 订单列表不直接暴露删除等危险操作。
- 发薪需要进入独立确认流程。
- 数据加载前不显示伪造的 0。
- 员工提交报工后能看到清楚的成功回执。

## 10. 信息缺口与后续调研

- 过去四周报工总数、编辑数、删除数和老板代改数。
- 工资争议和错误次数。
- 老板每周人工核对耗时。
- 626 条待质检的形成原因和业务影响。
