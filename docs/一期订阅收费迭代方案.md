# 一期订阅收费迭代方案

更新时间：2026-04-30

方案阶段：待实施

商业模式：人工收款或一次性微信支付，平台后台手动开通；暂不做自动续费。

## 1. 背景与目标

多工厂隔离完成后，系统已经具备按工厂独立管理数据的基础。下一步商业化不建议一开始就做复杂的自动续费、支付回调和会员营销，而是先用低风险方式验证客户付费意愿。

一期目标：

- 老板能在小程序里清楚看到自己工厂的服务状态、到期时间和开通方式。
- 平台管理员能在平台后台为每个工厂手动开通、延期、调整套餐。
- 到期提醒要明确，但不能突然影响工厂现场生产。
- 数据库设计要兼容后续接入微信支付自动开通。
- 页面文案遵循“联系平台管理员开通服务”，避免把小程序页面做成直接诱导外部扫码付款的收银页。

一期不做：

- 不做自动续费。
- 不做微信支付回调自动开通。
- 不做优惠券、分销、复杂营销活动。
- 不做按员工每日动态扣费。

## 2. 产品原则

目标用户包含中老年工厂老板，页面必须简单、直接、少选项、少术语。

设计原则：

- 先告诉用户“还能不能用、什么时候到期、找谁开通”。
- 所有关键按钮用大字号、大点击区域。
- 支付动作走人工确认，页面只承载说明、联系、复制资料。
- 到期处理采用提醒和宽限期，不直接让现场员工断工。
- 老板端只展示和本工厂有关的信息；平台端才展示跨工厂收费管理。

## 3. 推荐入口

### 老板端

新增页面：`pages/boss/subscription/subscription`

入口放在两个地方：

- `pages/boss/home/home` 顶部状态条：显示当前套餐、状态、到期日。
- `pages/boss/settings/settings` 列表项：`服务状态与续费`，作为长期固定入口。

状态条展示规则：

- 正常期：轻量展示，例如“标准版，有效期至 2026-12-31”。
- 剩余 15 天内：增强提醒，例如“服务即将到期，点击续费”。
- 宽限期：醒目提醒，例如“服务已到期，宽限期内仍可使用”。
- 宽限期结束：老板端进入续费引导页；员工端只提示联系老板。

### 平台端

扩展现有页面：`pages/platform/home/home`

每个工厂卡片新增：

- 套餐名称
- 服务状态
- 到期时间
- 剩余天数
- 开通/延期按钮

工厂详情区域新增“订阅管理”模块，平台管理员可执行：

- 开通套餐
- 延长到期时间
- 修改套餐
- 标记人工收款已确认
- 查看开通记录

### 员工端

员工端不放订阅入口。员工不是付费决策人，只需要看到必要提示：

- 宽限期内：不打扰员工。
- 宽限期结束：提示“工厂服务已到期，请联系老板处理”。

## 4. 老板端订阅页方案

页面名称：服务状态与续费

页面结构：

```text
当前服务
工厂名称：飞盛
当前版本：标准版
服务状态：正常使用中
到期时间：2026-12-31

开通方式
请联系平台管理员开通或续费。

需要发送给管理员的信息
工厂名称：飞盛
工厂码：A001
联系人：韩一帆
当前套餐：标准版
希望开通：标准版 / 1年

按钮
[复制开通信息]
[联系管理员]
```

二维码处理建议：

- 可以展示“管理员微信二维码”或“联系二维码”，但文案不要写成“扫码付款即可开通”。
- 更稳妥文案是：“请联系平台管理员确认开通。付款完成后，由管理员为工厂开通服务。”
- 若展示收款二维码，建议只在弹窗或联系信息区展示，不把页面标题、按钮和主流程做成纯支付页。

## 5. 套餐建议

一期建议按工厂收费，不按员工逐个收费。这样对工厂老板更容易理解，也方便销售。

建议套餐：

| 套餐 | 适用客户 | 建议价格 | 权益 |
| --- | --- | --- | --- |
| 试用版 | 新客户体验 | 14-30 天免费 | 功能基本开放，限制员工数或订单数 |
| 基础版 | 小厂 | 99-129 元/月，999-1299 元/年 | 订单、工序、报工、考勤 |
| 标准版 | 常规工厂 | 199-299 元/月，1999-2999 元/年 | 基础版 + 统计、导出、二维码打卡 |
| 专业版 | 多管理需求工厂 | 399-599 元/月，3999-5999 元/年 | 标准版 + 多管理员、更多容量、优先支持 |
| 企业版 | 定制客户 | 单独报价 | 私有化、定制报表、迁移服务 |

一期默认推荐“标准版年付”，页面不要同时展示太多价格，避免用户犹豫。销售沟通时可保留月付和年付。

## 6. 到期策略

推荐策略：

- 到期前 15 天：老板端轻提醒。
- 到期前 7 天：老板端强提醒。
- 到期后 7 天：宽限期，核心生产功能继续可用。
- 宽限期结束后：限制新增和修改，保留查看、导出、联系管理员。

限制建议：

| 功能 | 到期后宽限期内 | 宽限期结束后 |
| --- | --- | --- |
| 员工签到/签退 | 可用 | 不可用或仅提示联系老板 |
| 员工报工 | 可用 | 不可新增 |
| 老板查看数据 | 可用 | 可用 |
| 老板导出数据 | 可用 | 可用，便于交接和续费 |
| 新建订单/工序/员工 | 可用 | 不可新增 |
| 平台管理员开通 | 可用 | 可用 |

实际拦截口径建议一期偏温和：先拦新增订单、工序、员工、报工、二维码生成；查看历史数据和导出不拦。

## 8. 云函数设计

### 新增 billing 云函数

建议新增：`cloudfunctions/billing/index.js`

老板端接口：

- `getMySubscription`：返回当前工厂套餐、状态、到期时间、管理员联系方式。
- `getOpenRequestInfo`：返回可复制给管理员的开通信息。

平台端接口：

- `listPlans`：套餐列表。
- `openSubscription`：为工厂开通套餐。
- `extendSubscription`：延期。
- `changePlan`：修改套餐。
- `listBillingOrders`：查看收款/开通记录。
- `markManualPaymentPaid`：标记人工收款已确认。

### Entitlement 校验

建议在 `cloudfunctions/common/` 增加权限工具：

```js
requireEntitlement(caller, featureKey)
```

一期先接入高价值写操作：

- `order.create`
- `order.addProcess`
- `user.create`
- `worklog.submit`
- `qrcode.generate`
- `export.exportToFileV2`

查询类接口先不拦，减少客户数据焦虑。

## 9. 迁移方案

新增 init 动作：`migrate_billing_v1`

迁移步骤：

1. 创建默认套餐：试用版、基础版、标准版、专业版。
2. 为所有已有 `Organizations` 补充订阅字段。
3. 为老工厂 `org_home` 创建一条长期试用或内部赠送订阅，建议 6-12 个月。
4. 为其他已有工厂创建试用订阅，默认 30 天。
5. 写入 `Subscriptions` 历史记录。
6. 可选：回填近 3-6 个月 `UsageMonthly`。

迁移要求：

- 必须可重复执行。
- 必须分批处理，避免云函数 3 秒超时。
- 每批返回处理进度，方便在开发者工具控制台连续执行。
- 不修改业务数据，如订单、工序、报工、考勤。

## 10. 实施拆分

### 第 1 步：数据和后台能力

- 新增 `billing` 云函数。
- 新增 `migrate_billing_v1`。
- 平台后台展示订阅状态。
- 平台后台支持开通、延期、改套餐。

验收：

- 平台管理员能给任意工厂开通标准版。
- 开通后 `Organizations` 快速字段和 `Subscriptions` 记录一致。
- 重复执行迁移不重复创建脏数据。

### 第 2 步：老板端订阅页

- 新增 `pages/boss/subscription/subscription`。
- 老板首页加入订阅状态条。
- 设置页加入“服务状态与续费”入口。
- 支持复制开通信息。

验收：

- 老板能看懂当前状态和到期日。
- 点击复制后能把工厂名、工厂码、联系人、套餐意向发给管理员。
- 页面在小屏手机不溢出。

### 第 3 步：到期提醒和温和拦截

- 老板端按剩余天数展示提醒。
- 到期宽限期结束后拦截新增订单、工序、员工、报工、二维码生成。
- 员工端提示联系老板，不展示付款信息。

验收：

- 未到期工厂功能不受影响。
- 到期工厂仍可查看历史数据。
- 平台管理员开通后，限制立即解除。

### 第 4 步：运营数据和成本观察

- 补充 `UsageMonthly`。
- 平台端展示员工数、订单数、报工数、考勤数、导出次数。
- 用真实数据评估套餐员工上限和价格。

验收：

- 平台管理员能看到每个工厂的月度使用情况。
- 能筛出高频使用但低价套餐客户。

## 11. 成本与合规注意

成本关注：

- CloudBase 成本主要来自云函数调用、函数资源用量、数据库读写、数据库容量、云存储和文件下载。
- 报工、考勤、统计、导出是主要成本来源。
- 订阅上线前后要持续观察每个工厂的月度用量，避免低价套餐覆盖不了高频客户。
- 迁移和统计任务要分批，不能依赖长时间单次云函数。

合规关注：

- 一期页面定位为“联系管理员开通服务”，不要把小程序做成绕过小程序支付能力的收银台。
- 若后续做小程序内自动支付，应接入微信支付小程序支付能力，使用商户号、下单接口和支付回调。
- 页面文案避免“扫码立即付款自动开通”；建议使用“联系管理员确认开通”。

参考：

- 微信支付小程序支付快速开始：https://pay.wechatpay.cn/doc/v3/merchant/4015459512
- JSAPI/小程序下单接口：https://pay.wechatpay.cn/doc/v3/merchant/4012791897
- 微信支付二维码收款产品介绍：https://pay.wechatpay.cn/doc/v3/merchant/4012154495

## 12. 风险清单

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 到期后误拦生产功能 | 影响现场使用 | 设置 7 天宽限期，先拦新增，保留查看 |
| 人工收款漏开通 | 客户体验差 | 复制开通信息，平台后台开通记录留痕 |
| 套餐字段和组织字段不一致 | 状态判断混乱 | 开通接口同时更新 `Subscriptions` 和 `Organizations`，并写日志 |
| 云函数迁移超时 | 迁移失败 | 分批、可重复、返回进度 |
| 页面被理解为外部收款页 | 审核风险 | 文案改为联系管理员开通，不做直接付款闭环 |
| 价格过早固定 | 商业试错受限 | 一期价格作为运营建议，套餐表可配置 |

## 13. 自审结论

已检查：

- 产品入口覆盖老板端、平台端、员工端，没有让员工承担付费动作。
- 一期范围保持克制，只做人工开通和一次性收款记录，不做自动续费。
- 数据模型兼容后续微信支付自动化，不需要推倒重来。
- 迁移方案考虑了历史工厂、老工厂赠送期和云函数超时问题。
- 到期策略避免突然中断现场生产。
- 合规文案倾向“联系管理员开通”，不把页面设计成直接外部收款入口。

结论：方案可以作为下一轮开发依据。实施前需要最终确认套餐价格、老客户赠送周期、到期后是否允许员工继续签到/报工。
