# 飞盛 · 工厂员工数据管理小程序

服装加工厂的一体化生产管理 SaaS。把**考勤、计件报工、质检、订单、薪酬结算、报表导出**串成一条闭环工作流，微信小程序 + 云开发（CloudBase）实现，已上线并在真实工厂稳定运行 4 个月以上，目前稳定服务 10 家以上工厂、200 名以上用户（2026-09）。

**这个项目的第一原则：工资算得对 > 一切。** 计件工资直接对应工人当月拿多少钱，算错一次就失去信任。所以本仓库把绝大部分复杂度花在「价格口径正确」和「租户数据隔离」这两件事上，功能数量从来不是目标。

## 角色与主流程

四种角色：**工人 / 质检 / 老板 / 平台管理员**。

```
接单 → 派工 → 报工 → 质检 → 结算 → 发薪 → 报表导出
                ↑
            考勤 / 请假
```

- **工人**：定位围栏打卡、扫码打卡、按工序报工（填数量，实时预览金额）、查自己的工资明细
- **质检**：待检 / 已检流转，合格率统计
- **老板**：订单与工序全生命周期、批量派工、考勤与请假管理、工资核算与发薪、经营数据报表、导出
- **平台管理员**：多工厂（租户）管理与订阅计费

## 技术栈

原生微信小程序（WXML / WXSS / JS）+ 云函数（Node.js）+ CloudBase 数据库。无前端框架，无构建步骤。

## 架构要点

### 一、多租户隔离：`org_id` 只从鉴权态推导，绝不信前端

这是整个系统的安全地基。`cloudfunctions/common/auth-guard.js` 里的 `buildStrictAuthWhere()` 要求 `auth_user_id` **和** `auth_session_token` 同时存在，**缺一返回 null，没有任何兜底**；再校验用户 `status: 'active'`、其所属工厂 `status: 'active'`，任何查询异常一律 `return null`。

**这是 fail-closed —— 不存在「查不到就放行」的降级路径。** 业务云函数里没有一处从 `event` 取 `org_id`（仅平台超管接口按需指定操作哪个工厂，且每处前面都有 `requirePlatformAdmin()`）。

⭐ **一个被平台约束逼出来的解法**：云函数各自独立部署、**没有共享运行时**，所以 `auth-guard.js` 被**逐字节复制进 10 个业务函数目录**（md5 全部相同）。为了防止副本漂移，`tests/auth-guard-copies.test.js` 既比对字节一致，也断言每个 `index.js` 不含 `openid` 回退模式。选「复制 + 一致性测试」而不是硬上抽象，是权衡后的结果。

### 二、计件工资的三层价格防错

工序单价会变，但**已发过薪的历史绝不能被改写**。三层机制：

| 层 | 做什么 | 为什么需要 |
|---|---|---|
| **写时同步** | 老板改工序单价前，先查有没有已发薪记录命中，**命中就整体拒绝**；无冲突才改，并把该工序**所有未发薪**报工的快照价一起重写 | 让改价能追溯纠正未发薪部分 |
| **读时自愈** | 每次查工资/报工时，把仍未发薪记录展示的价强制对齐当前工序价；已发薪的保持历史快照不动 | 给「写时同步万一漏了的存量数据」兜底 |
| **发薪时固化** | 打勾发薪前，先把本次范围内未发薪报工的快照价、金额、工序名**固化落库，固化失败直接中止发薪** | 补掉一个真实存在过的口径漏洞：此前发薪只写总额、不回写结算价，导致明细会翻回旧快照价、与实发总额对不上 |

配套 `salary.repairSettlementPrices` 做存量对账修复：**默认 dry_run**，且**只有「按发薪当时口径重算总额 == 已记录总额」时才敢重写**，对不上账的一律不动、进 `manual_review`。

**发薪锁**：发薪记录的文档 id 是确定性的（`${org}_${user}_${month}` 或 `..._order_${orderId}`），天然防并发重复发薪。

### 三、订单完成锁，且可恢复

订单 `completed` 后拦截所有写操作入口，防止已完成订单被改动而销毁发薪凭证。老板可把 `completed` 改回 `active`（但**禁止 completed → cancelled**），恢复时**自动解锁该订单「按订单」发放的工资锁**并留审计字段；**「按月」发放的锁不自动解**，只提示冲突数量让老板自行处理——避免「恢复一个订单，悄悄解锁了别的订单同月的发薪记录」。

## 测试

```bash
npm run test:unit
```

当前 **309 个用例全部通过**（`node --test`，零外部依赖，秒级跑完）。测试重点覆盖：跨租户访问拒绝、鉴权副本一致性、计件金额唯一公式、已发薪数据不可变、时区边界。

⚠️ **本仓库没有 CI**，测试靠手动跑。端到端只验证首页可打开，不覆盖登录 / 报工 / 发薪 / 跨租户拒绝。

## 本地开发

1. 用微信开发者工具打开本项目根目录
2. 新建并绑定云开发环境
3. 右键 `cloudfunctions/` 下各函数 → 上传并部署
4. 首次初始化数据库（受控执行一次）：

```javascript
wx.cloud.callFunction({ name: 'init' }).then(console.log).catch(console.error)
```

## 已知边界（不吹的部分）

诚实列出当前真实存在的缺口，避免读者高估：

- **没有任何 AI / ML**。（早期调研过人脸识别登录与打卡，结论是当时不存在可用于「登录 + 考勤」的免费方案，主动决定不做，见 `docs/face-auth.md`。）
- **代码库内没有自建行为埋点**。运营数据依赖微信开发者后台自带的小程序数据看板；老板端的「数据中心」是**业务经营报表**（订单 / 工资 / 生产数据聚合），不是自建的用户行为分析。
- **批量派工不是原子操作**：分块并发写，**无事务、无回滚**，失败时只返回一句笼统提示，看不出哪几条没成功。
- **订阅收费是人工确权记账，不是支付系统**：全库没有 `requestPayment`，由管理员手动记录金额与到账状态——规避小程序支付类目的审核复杂度。
- **写操作无幂等保护**，配合客户端自动重试存在重复报工 / 补卡的风险。
- **`session_token` 无过期时间**，泄露后长期有效。
- 长订单的工序列表是「点击加载更多」式分页，不是虚拟列表；文档里「支持 150-200 道工序」是**设计稿目标**，实测处理过的最大订单是 **65-116 道工序**。
- 数据库有 5 个建表脚本里创建、但业务代码从未读写的**僵尸集合**。
- `cloudfunctions/billing/` 手写了一份等价的鉴权逻辑，**不在** `auth-guard-copies.test.js` 的守护名单里，改动共享鉴权口径时需人工同步。
- **`docs/` 里的运营数字都是文档撰写当天的快照，不随产品更新**（仓库没有数据同步机制）。比如 `docs/review/2026-07-11-product-engineering-ux-audit-handover.md` 里的工厂数、用户数是 2026-07-11 走查当天的数字；当前规模以本文开头为准。

## 开发方式

本项目用 **Spec Coding** 推进：先把需求规格写清楚，再由 AI 协作实现。`CLAUDE.md` / `AGENTS.md` 里显式写死了一条规矩——

> 「这一节是业务真相的唯一来源。**代码与本节冲突时，以本节为准，代码该改。**」

**规格高于代码，不是代码高于文档。** 高风险区（工资、发薪、租户隔离、时区）的改动必须先出 Plan：改动范围、涉及文件、数据字段、旧数据兼容、测试路径，**口径不确定先标「不确定」再确认，绝不猜**。

## 合规

内置隐私政策与用户协议页面，登录同意勾选框默认未勾选并做了版本化记录（`consent_version`），避免「登录即同意」。

- 不提交 `project.private.config.json`
- 代码中不出现密钥、Token、账号密码
- 核心链路手动回归：登录、打卡、报工、质检、发薪、导出
